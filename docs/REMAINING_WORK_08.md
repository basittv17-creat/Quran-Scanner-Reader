## Rights and authenticity checklist

- [ ] Identify the reciter, riwayah, performance style, master or session edition, publisher, original producer and authorized grantor. Record the grantor's chain of rights for the performance and sound recording as applicable.
- [ ] Archive the dated license or signed permission and exact release identifiers. Confirm the grant covers copying and permanent public distribution in this GitHub repository and source ZIP backups, including downstream clones and downloads. Record territory, term, attribution and any further conditions. Obtain separate permission for cuts or encoding changes if required.
- [ ] Record a manifest with source URL, retrieval date, immutable release ID, byte size and SHA-256 for each original file and each final MP3. Verify against the publisher's authenticated inventory when available. Record segmentation or encoding lineage and hash each final deliverable independently.
- [ ] Compare verse keys with the canonical 6,236-key set. Log missing, extra and duplicate keys and investigate identical hashes across different verse keys. Have a qualified reviewer listen to each final clip and record identity, verse boundaries, recitation edition, completeness, repeated phrases and any extraneous audio. Record who reviewed which file hash and when.
- [ ] Clear timing rights independently for the exact dataset revision and for distribution of converted TSVs. Record attribution and change notices. Collect the complete human review record described below.

## Timing intake

Use the existing [Phase 7 format](PHASE7_AUDIO_PACK_FORMAT.md) and [Phase 8 format](PHASE8_WORD_TIMING_FORMAT.md). Current source keeps up to eight local audio packs and one active timing pack. Audio is selected through the existing catalog. Timing is bound to the selected recording by its verse entry and exact audio/text digests. The ZIP manifest's attribution fields are declarations and require the supporting rights record above.

1. Freeze the reviewer inputs. Pin the recording release and MP3 SHA-256 per ayah, the timing release and original file SHA-256, and the exact UTF-8 canonical ayah SHA-256. Match by surah and ayah plus those hashes. Reciter name, bitrate, catalog ID and a similar-sounding performance are insufficient.
2. Use 1-based whitespace-delimited canonical word indices. Keep original Tanzil Arabic and diacritics byte-for-byte. Have a qualified reviewer listen to the exact final MP3 and approve each word's onset and end on the ayah-local clock in integer milliseconds. Log reviewer, date, method, clock origin, tool/version, decisions, unresolved verse keys and reviewed file hashes. Surah offsets need a documented mapping and fresh review on the final MP3, including any encoder delay or padding.
3. Require one ordered, nonoverlapping positive-length interval per canonical word. Permit gaps for silence. Require the final end within both the actual recording duration and 900,000 ms. Record explicit exceptions for repeats, restarts, introductory phrases or ambiguous boundaries. Hold any verse that cannot be accurately represented in the format. Track expected words, reviewed words and accepted timed verses per surah.
4. Build root-only packs with the existing Python scripts using the approved local inputs. The timing manifest stores the exact TSV, MP3 and canonical verse SHA-256 values plus word count. Verify ZIP integrity and compare accepted verse-key sets with all 6,236 ayat before describing coverage as complete. Exercise the existing local import and pack switching flow with an authorized device build. MP3 seeking is approximate and device listening evidence is pending.
5. Keep recordings and timing data out of source and backups while either grant, byte provenance or listening review is missing. Never relabel an estimate, forced alignment or synthetic test as human-reviewed timing.
