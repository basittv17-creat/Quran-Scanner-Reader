Gradle-generated checksums are an inventory of the bytes served during resolution. Any changed toolchain or variant needs its own reviewed entries. ## Advisories

- Gradle 8.10.2 is affected by published 8.x repository fallback and daemon/worker advisory ranges. Gradle 8.14.7 is a candidate that includes the October fixes and addresses November version-catalog and daemon registry issues. This repository has no tracked version catalog. AGP 8.7 requires at least Gradle 8.9. JetBrains lists Gradle up to 8.10 with caveats for KGP 2.0.21 and lists AGP through 8.5 in that KGP row. KGP 2.2.21 is a compatibility candidate for AGP 8.7.3 with Gradle 8.14, subject to the actual JDK 17 and four-task CI gates. Shared Gradle/CI edits require coordination with Work 10. [Gradle advisories](https://github.com/gradle/gradle/security/advisories) · [Gradle 8.14.7](https://docs.gradle.org/8.14.7/release-notes.html) · [AGP compatibility](https://developer.android.com/build/releases/about-agp) · [Kotlin compatibility](https://kotlinlang.org/docs/gradle-configure-project.html)
- The verified OCR AAR contains Tesseract, Leptonica, JPEG and PNG shared libraries across four ABIs. Each `libpngx.so` contains a 1.6.48 version string, consistent with the upstream tag. Camera and gallery pass a bitmap into `TessBaseAPI.setImage(Bitmap)`. At upstream tag `4.9.0` (`15c534717b1cb58261b58d4e4c1200c7f81f668c`), `ReadFile.readBitmap` calls JNI that locks Android bitmap pixels and creates a Leptonica Pix. Separate file and encoded-byte entry points call `pixRead` and `pixReadMem`. The app's reviewed OCR input path does not call those entry points. Android platform image decoding remains exposed to user-selected images, and this source trace does not establish whole-binary reachability or patch provenance. No verified patched Android OCR artifact was established. [OCR source](https://github.com/adaptech-cz/Tesseract4Android/tree/4.9.0) · [libpng advisories](https://github.com/pnggroup/libpng/security/advisories)
- JUnit is test-only. Its pinned 4.13.2 follows the fix for the published TemporaryFolder disclosure. The resolved graph still requires advisory assessment. [JUnit advisory](https://github.com/advisories/GHSA-269g-pwp5-87pp)

## Offline storage and Quran integrity

Audio and timing ZIP imports use private, unique staging directories, flat allowlists, duplicate rejection, decompressed byte caps and content validation before activation. Streaming extraction writes regular files and ignores archive symlink metadata. Staging cleanup checks canonical paths and leaves unexpected entries alone. Existing pack data, backups and local selection semantics were preserved. Low-space, power loss, OEM transfer and Android platform decoder behavior still require device QA.

The source manifest requests camera access and omits INTERNET. Cleartext traffic and backup are disabled. Cloud backup and device transfer exclude credential- and device-protected app data. The app uses on-device OCR and recitation from local imports. System document providers can obtain selected files independently of the app.

Local Python privacy, import, corpus and OCR checks cover 6 source-policy tests, 6 Tanzil importer tests, the audio and timing pack builder checks, and 15 OCR benchmark tests. All 6,236 Tanzil Uthmani v1.1 verses were compared byte-for-byte against the pinned source with the publisher notice retained.
